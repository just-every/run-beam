# xAPI learning and an authorized LRS

The owner opens **Integrations**, connects an LRS supporting xAPI 1.0.3, and explicitly authorizes statement and attachment transmission/readback. Credentials are encrypted on the server and are absent from learner launches, audit details and learning exports. Revoke the connection to refuse new launches and results. The installation administrator admits HTTPS hostnames with `BEAM_XAPI_HOSTS`; an empty list denies external connections. Redirects are refused. This is the same deployment-owned host-admission pattern as the LTI and webhook connections.

In a course draft, the owner adds an activity identity, same-origin launch address, objectives, procedure citations, the LRS connection, and a separate shared secret configured on the activity's server. The page supplies its producer username and Beam statement endpoint. Keep this secret on the provider's server. The course's named reviewer sees and publishes the exact activity and **completed-and-passed** rule. Changes require a new activity and reviewed revision; earlier revisions and statements remain immutable. Generic proposed drafts cannot introduce an activity mapping.

A learner opens the assigned activity from the course. Beam sends a stable connection-specific account pseudonym, activity IRI, endpoint and fresh attempt registration. It sends no name, email, internal member ID or producer/LRS credential. An open attempt resumes in the same human session; a fresh device/session replaces it. Each registration expires after four hours, on a parent-session revocation or changed assignment access, or when a terminal outcome ends it. A failed attempt can be followed by a new registration; old results cannot complete the new attempt.

## Activity server protocol

POST statements to `/api/beam/xapi/statements` with `Authorization: Basic <activity-id:shared-secret>` and `X-Experience-API-Version: 1.0.3`. Use the account actor, activity identity and `context.registration` supplied by the launch, an explicit UUID statement ID and ISO timestamp. PUT with `?statementId=<id>` is also supported. An exact accepted duplicate returns the original ID without another completion. Reusing an ID with different content is refused. This scoped producer credential is independent of a learner's browser session.

The supported profile admits Agent account identities and Activity objects, their ordinary definitions, result/score/response/duration, supported context and extensions, and attached binary evidence in standard `multipart/mixed` requests. The bridge bounds a batch to 20 statements, JSON to 2 MiB and total attachment bytes to 10 MiB. Each attachment needs its exact content type, length, SHA-256 and bytes; Beam does not retrieve remote `fileUrl` attachments. Groups, SubStatements, StatementRefs, supplied authority and unsupported context are refused. See the [ADL data specification](https://github.com/adlnet/xAPI-Spec/blob/1.0.3/xAPI-Data.md) and [communication specification](https://github.com/adlnet/xAPI-Spec/blob/1.0.3/xAPI-Communication.md).

Beam retains the original admitted statement, its canonical digest and original attachment bytes. It writes them to the authorized LRS and verifies the stored statement and attachment readback before accepting evidence. Network refusal leaves a visible pending statement with the sanitized failure; the activity operator may explicitly resubmit that same UUID. There are no automatic retries. Neither an LRS error nor altered readback grants completion.

Only one trusted statement explicitly reporting both `result.completion=true` and `result.success=true` satisfies the reviewed rule. Incomplete and failed outcomes remain separate; contradictory terminal results are refused. The exact assignment revision's native lessons, quiz, practical and attendance gates remain required. A completion stores activity, launch, registration, rule and revision lineage. Statements remain evidence and never certify competence.

**Inspect xAPI evidence** on the assigned course shows retained originals, delivery state and authenticated attachment downloads. Procedure changes include the activity's own cited title, objectives and launch metadata in the same impact rule as SCORM; a person replaces the original activity mapping. Data export includes safe activity/revision/actor/registration/statement/attachment records, independently retrievable bytes, counts and digests. Producer credentials, LRS configuration and authentication session IDs stay excluded. Installation archives additionally replace SCORM session capabilities with irreversible evidence identities, withhold producer/LRS credentials, and restore sessions and integrations as terminal. The same fence applies when importing older archives; retained runtime events, statements, attachments and completions remain readable.

The owner-only connection, explicit disclosure/consent, server-only producer trust, connection-specific pseudonyms and deny-by-default host admission are conservative defaults pending ct approval under PACK-003. PACK-004 and PACK-005 inherit the approved xAPI identity/custody policy before they use this bridge.

## Reproduce the real LRS journey

The committed `tests/beam/live-xapi.mjs` runs the actual Apache-2.0 [Yet Analytics SQL LRS](https://github.com/yetanalytics/lrsql), never a local substitute. Download its official standalone distribution (qualified with v0.9.9); it includes an Apple Silicon Java 21 runtime and SQLite. No employer account or held key is needed. Run a clean built candidate through the fleet heavy slot with `BEAM_LIVE_PROOF=1` and `BEAM_SQL_LRS_DIRECTORY` pointing to the extracted distribution. Add `--browser` to exercise the original vaccine-temperature activity and all Beam end states at 1440 and 390. Browser module and screenshot directory may be supplied through `BEAM_PLAYWRIGHT_MODULE` and `BEAM_EVIDENCE_DIR`.

The runner uses an in-memory LRS on loopback ports 18123/18124, synthetic credentials, a bounded JVM and an original server-scored activity. `BEAM_XAPI_LOCAL_SANDBOX=true` permits local HTTP only when Beam itself has a loopback origin; it never admits loopback on a hosted installation. It refuses an already occupied LRS port and stops only its own LRS, activity server and browser. Push CI uses the same public-door assertions with a fake solely at the LRS network edge; real sandbox and browser qualification run separately.
